    UD3. Desarrollo y despliegue de aplicaciones Back-End con Spring Boot

    2. Arquitectura de una aplicación Spring Boot

    En este apartado vamos a comenzar a desarrollar nuestra API REST con Spring Boot. Aprenderemos a organizar el código en diferentes paquetes y clases, de manera que cada elemento tenga una responsabilidad concreta.

    Utilizaremos como ejemplo una aplicación de gestión de tareas llamada gestortareas.

    En esta ocasión trabajaremos desde el principio con Spring Data JPA y PostgreSQL. De esta forma, las tareas se almacenarán en una base de datos y no se perderán al reiniciar la aplicación.

    2.1. Arquitectura por capas

    Cuando desarrollamos una aplicación, es importante separar las responsabilidades. No debemos concentrar toda la lógica en una única clase.

    En nuestra aplicación utilizaremos los siguientes elementos:

    Elemento Responsabilidad
    Controller Recibe las peticiones HTTP y devuelve las respuestas.
    Service Contiene la lógica de negocio.
    Repository Se encarga de acceder a los datos almacenados.
    Model Representa las entidades principales de nuestra aplicación.
    DTO Define los datos que recibimos y enviamos a través de la API.
    Mapper Convierte objetos Model en DTO y viceversa.

    El recorrido habitual de una petición será:

    1. El cliente realiza una petición HTTP.
    2. El Controller recibe la petición.
    3. El Controller utiliza el Service correspondiente.
    4. El Service ejecuta la lógica de negocio y utiliza el Repository cuando necesita consultar o modificar datos.
    5. El Repository accede a la base de datos mediante Spring Data JPA.
    6. El resultado vuelve al Controller, que utiliza el Mapper para preparar el DTO de respuesta.
    7. El Controller devuelve una respuesta HTTP al cliente.

    2.2. Organización de paquetes

    Dentro del paquete principal com.daw.vdg, crearemos la siguiente estructura:

    com.daw.vdg
│
├── VdgApplication.java
│
├── controller
│   └── TareaController.java
│
├── service
│   └── TareaService.java
│
├── repository
│   └── TareaRepository.java
│
├── model
│   └── Tarea.java
│
├── dto
│   ├── TareaRequestDTO.java
│   └── TareaResponseDTO.java
│
└── mapper
    └── TareaMapper.java

    Todos estos paquetes deben estar dentro de com.daw.vdg, donde se encuentra la clase principal anotada con @SpringBootApplication. Así, el escaneo de componentes de Spring podrá localizar nuestros controladores, servicios y mappers.

    En IntelliJ podemos crear cada paquete haciendo clic derecho sobre com.daw.vdg y seleccionando New → Package.

    2.3. Configuración de application.properties

    Antes de trabajar con entidades y repositorios, necesitamos configurar la conexión con PostgreSQL.

    Dentro de src/main/resources encontraremos el archivo:

    application.properties

    Este archivo permite configurar diferentes aspectos de nuestra aplicación, como su nombre, el puerto del servidor, la conexión con la base de datos y el comportamiento de Hibernate.

    Vamos a utilizar una configuración similar a la siguiente:

    # Nombre de la aplicación
spring.application.name=puertollano

# Puerto en el que se ejecutará la aplicación
server.port=8082

# Mostrar el banner de Spring Boot
spring.main.banner-mode=console

# Nivel de registro de logs
logging.level.root=INFO

# Configuración de la conexión con PostgreSQL
spring.datasource.url=jdbc:postgresql://localhost:5432/postgres
spring.datasource.username=franciscoaliahernandez
spring.datasource.password=
spring.datasource.driver-class-name=org.postgresql.Driver

# Configuración de JPA e Hibernate
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.default_schema=public
spring.jpa.database-platform=org.hibernate.dialect.PostgreSQLDialect

    Explicación de las propiedades

    Propiedad Descripción
    spring.application.name Nombre identificativo de la aplicación.
    server.port Puerto en el que escuchará el servidor web.
    spring.main.banner-mode Controla la visualización del banner de Spring Boot.
    logging.level.root Establece el nivel general de los registros de la aplicación.
    spring.datasource.url URL de conexión con la base de datos.
    spring.datasource.username Usuario de PostgreSQL.
    spring.datasource.password Contraseña del usuario de PostgreSQL.
    spring.datasource.driver-class-name Driver JDBC utilizado para conectarse a PostgreSQL.
    spring.jpa.hibernate.ddl-auto Define cómo Hibernate gestiona la estructura de las tablas.
    spring.jpa.show-sql Permite mostrar en consola las consultas SQL generadas.
    spring.jpa.properties.hibernate.default_schema Esquema de PostgreSQL que se utilizará por defecto.
    spring.jpa.database-platform Dialecto SQL utilizado por Hibernate.

    Importante sobre la conexión:

    • En localhost:5432 indicamos que PostgreSQL está instalado en nuestro propio ordenador y escucha en el puerto 5432.
    • El último elemento de la URL, postgres, es el nombre de la base de datos a la que queremos conectarnos. En este ejemplo utilizamos la base de datos postgres, que suele existir por defecto.
    • El usuario y la contraseña deben corresponder a un usuario real de PostgreSQL.
    • Si el usuario tiene contraseña, debemos escribirla en spring.datasource.password. No debemos dejarla vacía salvo que PostgreSQL esté configurado realmente para permitir esa conexión sin contraseña.

    ¿Qué significa ddl-auto?

    La propiedad spring.jpa.hibernate.ddl-auto permite indicar qué debe hacer Hibernate con la estructura de la base de datos.

    Los valores más habituales son:

    Valor Comportamiento
    none No modifica el esquema de la base de datos.
    validate Comprueba que las tablas coinciden con las entidades.
    update Actualiza el esquema para adaptarlo a las entidades sin eliminar los datos existentes de forma general.
    create Crea de nuevo el esquema al iniciar la aplicación.
    create-drop Crea el esquema al iniciar y lo elimina al cerrar la aplicación.

    Durante el desarrollo utilizaremos:

    spring.jpa.hibernate.ddl-auto=update

    Así, cuando creemos una entidad nueva, Hibernate podrá generar la tabla correspondiente.

    Importante: update, create y create-drop son opciones pensadas para desarrollo y aprendizaje. En aplicaciones reales debemos gestionar los cambios de esquema mediante herramientas de migración como Flyway o Liquibase, y evitar que Hibernate modifique automáticamente la base de datos de producción.

    Seguridad de las credenciales

    No debemos subir contraseñas reales al repositorio de GitHub. Para un proyecto compartido podemos utilizar variables de entorno:

    spring.datasource.username=${DB_USER}
spring.datasource.password=${DB_PASSWORD}

    De esta manera, cada ordenador configura sus propias credenciales sin guardarlas en el código fuente.

    2.4. Model: representación de los datos

    Un Model representa un objeto de nuestro dominio, es decir, un elemento con el que trabaja nuestra aplicación.

    En nuestro gestor de tareas necesitamos representar una tarea con los siguientes atributos:

    Atributo Tipo Descripción
    id Long Identificador de la tarea.
    titulo String Título de la tarea.
    descripcion String Descripción de la tarea.
    completada boolean Indica si la tarea está finalizada.

    Crearemos el paquete model y dentro la clase Tarea.

    Tarea.java

    package com.daw.vdg.model;

import jakarta.persistence.*;

@Entity
@Table(name = "tareas")
public class Tarea {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 150)
    private String titulo;

    @Column(length = 1000)
    private String descripcion;

    @Column(nullable = false)
    private boolean completada;

    // Constructor vacío necesario para JPA
    public Tarea() {
    }

    // Constructor sin ID: lo genera la base de datos
    public Tarea(String titulo, String descripcion, boolean completada) {
        this.titulo = titulo;
        this.descripcion = descripcion;
        this.completada = completada;
    }

    public Long getId() {
        return id;
    }

    public void setId(Long id) {
        this.id = id;
    }

    public String getTitulo() {
        return titulo;
    }

    public void setTitulo(String titulo) {
        this.titulo = titulo;
    }

    public String getDescripcion() {
        return descripcion;
    }

    public void setDescripcion(String descripcion) {
        this.descripcion = descripcion;
    }

    public boolean isCompletada() {
        return completada;
    }

    public void setCompletada(boolean completada) {
        this.completada = completada;
    }
}

    Explicación de las anotaciones JPA

    @Entity

    Indica que la clase representa una entidad persistente. Hibernate utilizará esta clase para almacenar y recuperar información de la base de datos.

    @Table

    Permite indicar el nombre de la tabla asociada a la entidad:

    @Table(name = "tareas")

    En este caso, la tabla se llamará tareas.

    @Id

    Indica qué atributo representa la clave primaria de la tabla.

    @GeneratedValue

    Indica que el identificador se genera automáticamente:

    @Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

    Con GenerationType.IDENTITY delegamos la generación del identificador en la base de datos. En PostgreSQL se utilizará una columna con generación de identidad.

    Por tanto, cuando creemos una tarea no tendremos que asignarle manualmente un ID.

    @Column

    Permite configurar las características de una columna:

    @Column(nullable = false, length = 150)
private String titulo;

    En este caso, el título será obligatorio y tendrá una longitud máxima de 150 caracteres.

    ¿Por qué necesitamos un constructor vacío?

    public Tarea() {
}

    JPA necesita poder crear instancias de las entidades mediante reflexión. Por eso debemos proporcionar un constructor sin parámetros, que puede ser public o protected.

    2.5. DTO: objetos para transferir datos

    DTO significa Data Transfer Object.

    Es un objeto que utilizamos para definir qué información entra o sale de nuestra API.

    Podríamos devolver directamente una entidad Tarea desde el Controller, pero es preferible separar los objetos internos de los datos que exponemos al exterior.

    Esto nos permite:

    • Decidir qué atributos recibe el cliente.
    • Decidir qué información devolvemos.
    • Evitar exponer directamente nuestras entidades.
    • Modificar el modelo interno sin tener que cambiar necesariamente el formato de la API.

    Vamos a crear dos DTO diferentes.

    TareaRequestDTO

    Representa los datos que el cliente envía cuando quiere crear o actualizar una tarea.

    No necesitamos recibir el identificador porque lo genera PostgreSQL.

    package com.daw.vdg.dto;

public record TareaRequestDTO(
        String titulo,
        String descripcion,
        boolean completada
) {
}

    TareaResponseDTO

    Representa los datos que nuestra API devuelve al cliente. En este caso sí incluimos el identificador.

    package com.daw.vdg.dto;

public record TareaResponseDTO(
        Long id,
        String titulo,
        String descripcion,
        boolean completada
) {
}

    Estamos utilizando record, una característica disponible desde Java 16.

    Los records permiten crear clases destinadas principalmente a transportar datos, evitando escribir manualmente constructores, getters, equals(), hashCode() y toString().

    Por ejemplo, podemos acceder al título mediante:

    String titulo = tareaResponseDTO.titulo();

    Diferencia importante:

    • TareaRequestDTO: representa los datos que recibimos.
    • TareaResponseDTO: representa los datos que devolvemos.

    Más adelante incorporaremos validaciones a los DTO para comprobar que los datos recibidos son correctos.

    2.6. Mapper: conversión entre objetos

    Tenemos dos tipos de objetos:

    • Model: representa los datos con los que trabaja nuestra aplicación.
    • DTO: representa los datos que intercambiamos con el cliente.

    Necesitamos convertir unos objetos en otros. Para ello utilizaremos un Mapper.

    Crearemos el paquete mapper y dentro la clase TareaMapper.

    TareaMapper.java

    package com.daw.vdg.mapper;

import com.daw.vdg.dto.TareaRequestDTO;
import com.daw.vdg.dto.TareaResponseDTO;
import com.daw.vdg.model.Tarea;
import org.springframework.stereotype.Component;

@Component
public class TareaMapper {

    public Tarea toModel(TareaRequestDTO dto) {

        return new Tarea(
                dto.titulo(),
                dto.descripcion(),
                dto.completada()
        );
    }

    public TareaResponseDTO toResponse(Tarea tarea) {

        return new TareaResponseDTO(
                tarea.getId(),
                tarea.getTitulo(),
                tarea.getDescripcion(),
                tarea.isCompletada()
        );
    }
}

    Hemos creado dos métodos:

    toModel()

    Recibe un TareaRequestDTO y devuelve un objeto Tarea. Lo utilizaremos cuando recibamos información del cliente y necesitemos trabajar con ella dentro de nuestra aplicación.

    Observa que no asignamos el ID: lo generará la base de datos.

    toResponse()

    Recibe un objeto Tarea y devuelve un TareaResponseDTO. Lo utilizaremos cuando queramos devolver información al cliente.

    La anotación @Component indica a Spring que debe gestionar esta clase como un bean. Así podremos inyectarla en el Controller en lugar de crearla manualmente con new.

    2.7. Repository: acceso a los datos

    El Repository es la capa encargada de comunicarse con la base de datos.

    Spring Data JPA nos permite crear repositorios sin tener que implementar manualmente las operaciones CRUD más habituales.

    Crearemos el paquete repository y dentro la interfaz TareaRepository.

    TareaRepository.java

    package com.daw.vdg.repository;

import com.daw.vdg.model.Tarea;
import org.springframework.data.jpa.repository.JpaRepository;

public interface TareaRepository extends JpaRepository<Tarea, Long> {
}

    Observa que no hemos escrito ningún método.

    Al extender de JpaRepository, Spring Data JPA nos proporciona automáticamente operaciones como:

    Método Función
    findAll() Obtiene todos los registros.
    findById(id) Busca un registro por su identificador.
    save(objeto) Inserta o actualiza un registro.
    deleteById(id) Elimina un registro por su identificador.
    existsById(id) Comprueba si existe un registro.
    count() Devuelve el número de registros.

    En la declaración:

    JpaRepository<Tarea, Long>

    Indicamos dos tipos:

    • Tarea: la entidad con la que trabajará el repositorio.
    • Long: el tipo de dato de su clave primaria.

    No necesitamos añadir @Repository expresamente porque Spring Data JPA genera y registra automáticamente la implementación de esta interfaz.

    2.8. Service: lógica de negocio

    El Service contiene la lógica de negocio de nuestra aplicación.

    En nuestro gestor de tareas será responsable de:

    • Obtener todas las tareas.
    • Buscar una tarea por su identificador.
    • Crear una tarea.
    • Actualizar una tarea.
    • Eliminar una tarea.

    El Controller no debería contener toda esta lógica. Su responsabilidad será recibir las peticiones y delegar el trabajo en el Service.

    TareaService.java

    package com.daw.vdg.service;

import com.daw.vdg.model.Tarea;
import com.daw.vdg.repository.TareaRepository;
import org.springframework.http.HttpStatus;
import org.springframework.stereotype.Service;
import org.springframework.web.server.ResponseStatusException;

import java.util.List;

@Service
public class TareaService {

    private final TareaRepository tareaRepository;

    public TareaService(TareaRepository tareaRepository) {
        this.tareaRepository = tareaRepository;
    }

    public List<Tarea> obtenerTodas() {
        return tareaRepository.findAll();
    }

    public Tarea obtenerPorId(Long id) {

        return tareaRepository.findById(id)
                .orElseThrow(() -> new ResponseStatusException(
                        HttpStatus.NOT_FOUND,
                        "No se ha encontrado la tarea"
                ));
    }

    public Tarea crear(Tarea tarea) {
        return tareaRepository.save(tarea);
    }

    public Tarea actualizar(Long id, Tarea datosActualizados) {

        Tarea tarea = obtenerPorId(id);

        tarea.setTitulo(datosActualizados.getTitulo());
        tarea.setDescripcion(datosActualizados.getDescripcion());
        tarea.setCompletada(datosActualizados.isCompletada());

        return tareaRepository.save(tarea);
    }

    public void eliminar(Long id) {

        Tarea tarea = obtenerPorId(id);

        tareaRepository.delete(tarea);
    }
}

    Explicación de la anotación @Service

    @Service
public class TareaService {

    La anotación @Service indica a Spring que esta clase contiene lógica de negocio y que debe gestionarla como un bean.

    Inyección de dependencias por constructor

    private final TareaRepository tareaRepository;

public TareaService(TareaRepository tareaRepository) {
    this.tareaRepository = tareaRepository;
}

    El Service necesita un Repository para acceder a los datos.

    En lugar de crear manualmente un objeto mediante new TareaRepository(), dejamos que Spring proporcione la implementación correspondiente.

    Esto es posible gracias a la inyección de dependencias.

    Utilizamos inyección por constructor, una de las formas recomendadas de trabajar con Spring.

    No necesitamos @Autowired cuando existe un único constructor.

    Buscar una tarea por ID

    return tareaRepository.findById(id)
        .orElseThrow(() -> new ResponseStatusException(
                HttpStatus.NOT_FOUND,
                "No se ha encontrado la tarea"
        ));

    El método findById() devuelve un Optional<Tarea> porque puede que la tarea no exista.

    Con orElseThrow() indicamos que, si no encontramos la tarea, debemos lanzar una excepción HTTP 404 (Not Found).

    Crear una tarea

    public Tarea crear(Tarea tarea) {
    return tareaRepository.save(tarea);
}

    El método save() guarda la entidad en la base de datos. Como la tarea es nueva y su ID todavía es null, PostgreSQL genera automáticamente el identificador.

    Actualizar una tarea

    Primero recuperamos la entidad existente mediante obtenerPorId(id). Después modificamos sus atributos y guardamos los cambios.

    Es importante actualizar la entidad recuperada, conservando su identificador, en lugar de crear una entidad nueva sin ID.

    Eliminar una tarea

    Primero comprobamos que la tarea existe y después la eliminamos mediante el Repository.

    2.9. Controller: recibir peticiones HTTP

    El Controller es la capa que se comunica directamente con el cliente.

    Su responsabilidad consiste en:

    • Recibir peticiones HTTP.
    • Obtener los parámetros enviados por el cliente.
    • Invocar los métodos del Service.
    • Transformar los resultados mediante el Mapper.
    • Devolver respuestas HTTP.

    Crearemos el paquete controller y dentro la clase TareaController.

    TareaController.java

    package com.daw.vdg.controller;

import com.daw.vdg.dto.TareaRequestDTO;
import com.daw.vdg.dto.TareaResponseDTO;
import com.daw.vdg.mapper.TareaMapper;
import com.daw.vdg.model.Tarea;
import com.daw.vdg.service.TareaService;

import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/tareas")
public class TareaController {

    private final TareaService tareaService;
    private final TareaMapper tareaMapper;

    public TareaController(
            TareaService tareaService,
            TareaMapper tareaMapper
    ) {
        this.tareaService = tareaService;
        this.tareaMapper = tareaMapper;
    }

    @GetMapping
    public ResponseEntity<List<TareaResponseDTO>> obtenerTodas() {

        List<TareaResponseDTO> respuesta = tareaService.obtenerTodas()
                .stream()
                .map(tareaMapper::toResponse)
                .toList();

        return ResponseEntity.ok(respuesta);
    }

    @GetMapping("/{id}")
    public ResponseEntity<TareaResponseDTO> obtenerPorId(
            @PathVariable Long id
    ) {

        Tarea tarea = tareaService.obtenerPorId(id);

        return ResponseEntity.ok(tareaMapper.toResponse(tarea));
    }

    @PostMapping
    public ResponseEntity<TareaResponseDTO> crear(
            @RequestBody TareaRequestDTO dto
    ) {

        Tarea nuevaTarea = tareaMapper.toModel(dto);

        Tarea tareaCreada = tareaService.crear(nuevaTarea);

        return ResponseEntity
                .status(HttpStatus.CREATED)
                .body(tareaMapper.toResponse(tareaCreada));
    }

    @PutMapping("/{id}")
    public ResponseEntity<TareaResponseDTO> actualizar(
            @PathVariable Long id,
            @RequestBody TareaRequestDTO dto
    ) {

        Tarea datosActualizados = tareaMapper.toModel(dto);

        Tarea tareaActualizada = tareaService.actualizar(
                id,
                datosActualizados
        );

        return ResponseEntity.ok(
                tareaMapper.toResponse(tareaActualizada)
        );
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> eliminar(@PathVariable Long id) {

        tareaService.eliminar(id);

        return ResponseEntity.noContent().build();
    }
}

    Analizamos las anotaciones

    @RestController

    Indica que la clase es un controlador REST. Spring recibe las peticiones HTTP y convierte los objetos devueltos a formatos como JSON.

    Combina las funcionalidades de @Controller y @ResponseBody.

    @RequestMapping

    @RequestMapping("/api/tareas")

    Define la ruta base de todos los endpoints de este controlador.

    @GetMapping

    Se utiliza para recibir peticiones HTTP GET.

    @PostMapping

    Se utiliza para recibir peticiones HTTP POST.

    @PutMapping

    Se utiliza para recibir peticiones HTTP PUT.

    @DeleteMapping

    Se utiliza para recibir peticiones HTTP DELETE.

    @PathVariable

    Permite recoger un valor incluido en la propia URL.

    Por ejemplo:

    @GetMapping("/{id}")
public ResponseEntity<TareaResponseDTO> obtenerPorId(
        @PathVariable Long id
) {

    Si recibimos la petición GET /api/tareas/5, el parámetro id tendrá el valor 5.

    @RequestBody

    Permite convertir el cuerpo de una petición HTTP, normalmente enviado en formato JSON, en un objeto Java.

    Por ejemplo, al recibir:

    {
    "titulo": "Estudiar Spring Boot",
    "descripcion": "Repasar arquitectura por capas",
    "completada": false
}

    Spring convierte automáticamente el JSON en un objeto TareaRequestDTO.

    ¿Qué es ResponseEntity?

    ResponseEntity representa una respuesta HTTP completa.

    Nos permite controlar:

    • El código de estado HTTP.
    • Las cabeceras de la respuesta.
    • El cuerpo de la respuesta.

    Por ejemplo:

    return ResponseEntity.ok(respuesta);

    Devuelve el código HTTP 200 OK junto con los datos.

    return ResponseEntity
        .status(HttpStatus.CREATED)
        .body(respuesta);

    Devuelve el código HTTP 201 Created.

    return ResponseEntity.noContent().build();

    Devuelve el código HTTP 204 No Content, sin cuerpo de respuesta.

    2.10. Probamos nuestra API REST

    Antes de ejecutar la aplicación, debemos comprobar que:

    1. PostgreSQL está iniciado.
    2. Existe la base de datos indicada en spring.datasource.url.
    3. El usuario y la contraseña configurados son correctos.
    4. Las dependencias de Maven están descargadas.

    Ejecutamos la aplicación desde VdgApplication.

    Como hemos configurado el puerto 8082, nuestra API tendrá como dirección base:

    http://localhost:8082/api/tareas

    Podemos probar los endpoints utilizando Postman.

    Obtener todas las tareas

    Petición:

    GET http://localhost:8082/api/tareas

    Si todavía no hay tareas, devolverá una lista vacía:

    []

    Crear una tarea

    Petición:

    POST http://localhost:8082/api/tareas

    En Postman seleccionamos Body → raw → JSON y enviamos:

    {
    "titulo": "Estudiar Spring Boot",
    "descripcion": "Aprender a crear una API REST",
    "completada": false
}

    Respuesta esperada:

    {
    "id": 1,
    "titulo": "Estudiar Spring Boot",
    "descripcion": "Aprender a crear una API REST",
    "completada": false
}

    El código HTTP será 201 Created. El ID lo habrá generado PostgreSQL.

    Obtener una tarea por su identificador

    Petición:

    GET http://localhost:8082/api/tareas/1

    Respuesta esperada:

    {
    "id": 1,
    "titulo": "Estudiar Spring Boot",
    "descripcion": "Aprender a crear una API REST",
    "completada": false
}

    Actualizar una tarea

    Petición:

    PUT http://localhost:8082/api/tareas/1

    Body:

    {
    "titulo": "Estudiar Spring Boot y REST",
    "descripcion": "Completar los ejercicios de la unidad",
    "completada": true
}

    La API devolverá la tarea actualizada con el código 200 OK.

    Eliminar una tarea

    Petición:

    DELETE http://localhost:8082/api/tareas/1

    Si la eliminación se realiza correctamente, devolveremos el código 204 No Content.

    Si intentamos consultar una tarea que no existe, obtendremos un error 404 Not Found.
